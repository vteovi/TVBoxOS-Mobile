## 2.5.6 release 构建失败诊断（缓存问题，非代码错误）
- 现象：compileReleaseKotlin 报 HomeFragment/FastSearchActivity/CollectActivity/SettingActivity 找不到 ApiConfig 的 homeSourceBean/LoadConfigCallback/getSource/getIjkCodes/sourceBeanList/setSourceBean（Unresolved 或 private）。

- 解决：无需改代码；用户执行 `rm -rf app/build && ./gradlew assembleRelease`（或 clean）强制重编译即可。所有 20+ 错误同一根因。
- **第二次构建仍失败**：用户按上述在 PowerShell 跑 `rm -rf app/build` 实际未生效——PowerShell 里 `rm` 是 `Remove-Item`、不认 `-rf` 参数（报 NamedParameterNotFound），`cd /d/...` 也解析错（变成 `D:\d\...`）。故 app/build 没删、缓存原封不动，Gradle 继续用旧 ApiConfig.class 报错。
- **正确清理命令（PowerShell）**：`Remove-Item -Recurse -Force app\build` 然后 `.\gradlew.bat assembleRelease --console=plain`；或直接 `.\gradlew.bat clean assembleRelease`。Git Bash 下才是 `rm -rf app/build`。

## ⚠️ 2.5.6 第三次构建仍失败 —— 真正根因 = Kotlin 编译守护进程内存缓存
- 用户按"删 app/build + gradlew --stop + assembleRelease"重跑，**同样报错**。三次构建日志 `:app:compileReleaseJavaWithJavac` 任务全程未出现（因 Kotlin 先编译读 Java 源码模型，Kotlin 失败在前 javac 没机会跑)。
- 排查：全仓库仅一份 ApiConfig.java（app/src/main/java），无重复类/无 release sourceSet 覆盖；gradle.properties **未开** org.gradle.caching（排除构建缓存回放）；LoadConfigCallback 在 880c516 引入、getSourceBeanList 在 a78bdcc 引入（旧符号，非代码引用不存在的 API）。源码 100% 正确。
- **真正根因**：KotlinCompileDaemon（独立常驻 java 进程）持有 2.5.3 时代的 ApiConfig Java 分析缓存（sourceBeanList 当时是 public 字段、LoadConfigCallback 当时可能未引入）。`gradlew --stop` 只停 **Gradle** 守护进程，**不停 Kotlin 守护进程**；删 app/build 只清了磁盘缓存，但该进程内存模型仍陈旧 → Kotlin 一直用旧 ApiConfig 模型报错。
- **根治命令（PowerShell，必须杀掉 Kotlin 守护进程）**：
  `Get-Process -Name java -ErrorAction SilentlyContinue | Stop-Process -Force`  （同时杀 Gradle+Kotlin 守护进程）
  `Remove-Item -Recurse -Force app\build`
  `.\gradlew.bat assembleRelease --console=plain`
  （轻量替代：`.\gradlew.bat --stop` 不够，必须显式杀 java 进程；勿删项目级 .gradle 以免重下依赖）
- 教训：本仓库 Kotlin 守护进程缓存极顽固，凡改了 ApiConfig.java 等被 Kotlin 大量引用的 Java 公共 API 后，若之前有过 kill java.exe 中断构建，重编前务必先杀 KotlinCompileDaemon 进程，否则会反复报"Unresolved/private"假错。

## ✅ 2.5.6/2.5.7 构建失败——真正根因更正（不是缓存！是代码 bug）
- **用户杀 java + 删 app/build + 重构建，同样的 27 个错误逐字节复现** → 彻底排除"Kotlin 守护进程内存缓存"假设（进程都杀了、磁盘都清了还一样）。上面两条缓存诊断均为误判，作废。
- **真实根因**：a80a8e2 改 `ApiConfig.readContentConfig`（file:// 分支）时，**多写了一个右花括号**（`ApiConfig.java` 原 359 行）。该 `}` 把 `ApiConfig` 类提前在第 359 行关闭，导致其后声明的所有 public 成员（`LoadConfigCallback` 768 / `getSource` 782 / `setSourceBean` 788 / `getSourceBeanList` 805 / `getHomeSourceBean` 817 / `getIjkCodes` 870）全部落到类外，对 Kotlin 不可见。
- 表现吻合：第 57/63 行 private 字段 `sourceBeanList`/`ijkCodes` 在 359 行之前 → Kotlin 看得到但报"private"；其后所有 public getter → "Unresolved"。Kotlin 调用方式本身没错（`.sourceBeanList`/`.ijkCodes`/`.homeSourceBean` 本应通过 public getter 解析）。
- **修复**：删掉多余 `}`（现 358 行正常关方法，359 变空行）。用 Python 括号平衡扫描确认 depth=0、类正确闭合。所有 27 个错误同此一处，删括号即全部消失。
- **结论**：这是真实语法错误，不是缓存。此前"删缓存/杀守护进程"建议无害但无效；真正修复是改代码。教训——改 Java try-with-resources 结构后务必做括号平衡自检（尤其嵌套大改），不能只看 diff 上下文。

## ⚠️ 2.5.8 仍弹存储窗——根因：player 模块 manifest 又带回存储权限
- 用户装 2.5.8 后仍弹同样窗。根因：`:player` 模块（ijkplayer 封装，被 `:app` 依赖）的 `player/src/main/AndroidManifest.xml` 第 10-11 行声明了 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE`，Gradle manifest merger 会把它合并进最终 APK → 应用层删了也没用。
- 修复：
  - `player/src/main/AndroidManifest.xml` 删这两行存储权限（player 只做播放，不需要访问共享存储）。
  - 应用层 `app/src/main/AndroidManifest.xml` 加 `xmlns:tools` + 一组 `<uses-permission ... tools:node="remove">`，覆盖 READ/WRITE_EXTERNAL_STORAGE、MANAGE_EXTERNAL_STORAGE、READ_MEDIA_IMAGES/VIDEO/AUDIO —— 任何库合并进来的存储/媒体权限都会被强制剔除，最终 APK 的 manifest 不含这些权限，系统永不弹窗，库代码 requestPermissions 会立即失败（不弹窗）。
- 教训：TVBox 这类多模块项目改权限，必须**逐模块**查 AndroidManifest.xml，且最终用 `tools:node="remove"` 兜底最稳。
