## 订阅源切换本地缓存增强（v2.27.2 / versionCode 347，已本地提交 cc3995e，未发布）
- 需求：用户反馈切换订阅源（如 box.iqinu.com）有时加载不成功、不显示内容，希望缓存到本地，下次切换直接读缓存、有更新再同步。
- 诊断：`ApiConfig.loadConfig` 其实已有「按 URL 缓存、切换先读缓存秒出」逻辑，但两个薄弱点导致偶发空白：
  1. **缓存损坏不自愈**——`parseJson` 抛异常被吞掉→当无缓存→落网络，网络再抖就彻底空白，且坏缓存永不删除。
  2. **后台刷新无「是否变化」判断**——每次都重抓重解，没做内容比对。
- 改法（`ApiConfig.java`）：
  - 读缓存时若 `parseJson` 抛异常 → 删除坏缓存 + 删除 `.meta` 自愈。
  - 新增 `<md5(url)>.meta` 元信息（JSON：`hash` + `time`）。后台 OkGo 拉回内容后算 `MD5.string2MD5(json)` 与 `cachedHash` 比对：**相同则只更新时间戳、不重解/不回调 UI**（避免无谓闪烁）；**不同才 parseJson + 写缓存 + `callback.success(false)` 刷新**。
  - `LoadConfigCallback` 增加 `default void success(boolean fromCache)`（fromCache=true 表示来自本地缓存），旧调用方（HomeFragment）不受影响。
- 版本：PATCH +1 → 2.27.2 / versionCode 347；`build.gradle` 已改，`update.json`/README 待「发布」时回写（避免指向尚不存在的 Release）。
- 注：仅普通切换路径（useCache=false）走「缓存秒出 + 后台条件刷新」；设置页导航（CACHE_CONFIG_CHANGED=true→useCache=true）仍只渲染缓存、不联网。

### v2.28.0 切源秒开优化（2026-11-03 晚）
- **切源几秒延迟的真正主因**：`ApiConfig.loadJar` 只用单一全局缓存 `filesDir/csp.jar`，不同订阅源的 jar 互相覆盖 → 每次切源 md5 不匹配都要重下几 MB jar，而 jar 加载完成前首页不渲染。

- 缓存文件名用带 `img+` 前缀的原始 jarUrl 做 MD5（前缀稳定，命中无影响）。

### v2.28.2 回归修复：撤 fit()/pause/prefetch（2026-11-03 晚）
- **用户反馈 2.28.1 后"更卡了 + 同一画面来回上下动"**。复盘：① `Picasso.fit()` 在 RecyclerView 里是已知坑——依赖 View 实时尺寸，复用/重排时反复 defer 请求并触发布局，表现为原地抖动；② `setItemViewCacheSize(36)` 缓存 36 张已解码图 → 内存/GC 压力；③ `pauseTag/resumeTag` 在 resume 时一次性放开大量请求 → 瞬时卡顿；④ `setInitialPrefetchItemCount` 让滚动时并发解码更多图。
- **另一处更隐蔽的错误**：`resize(屏宽÷列数)` 在大屏少列数时目标尺寸可能大于原图（如 300×450 原图 → 853×1280），Picasso 会**放大解码**，单张从 ~0.5MB 涨到 ~4MB，比不加 resize 更糟。必须配 `onlyScaleDown()`（只缩不放）。
- **最终保留**：resize+onlyScaleDown、同图跳过重复请求（`setTag(R.id.ivThumb, pic)`）、`setItemAnimator(null)`（消除加载更多批量淡入掉帧）、`itemViewCacheSize=min(max(8,span*3),15)`、RatioShadowLayout 的 Hawk 静态缓存。
- 设置改 POSTER_SIZE / LANDSCAPE_CARD 时要调 `GridAdapter.resetDecodeSize()`。
- **教训**：RecyclerView 列表图优化优先用「固定/估算尺寸 + onlyScaleDown」，不要用 fit()；不要用静态共享 RecycledViewPool（泄漏 Activity）。
- 构建验证 BUILD SUCCESS，提交 d2e9d7d，**未推送**。

### v2.28.3 掉帧定位到「图片加载完成触发整屏重排」（2026-11-03 晚）
- **用户关键反馈**：往下滑（回看已加载内容）很流畅，往上滑（新内容、图片还没加载出来）掉帧。→ 排除绘制层级（ShadowLayout 的 clipPath 是持续成本，回看也顺，说明不是主因），锁定「图片异步加载完成的那一刻」。
- **根因**：`ImageView.setImageDrawable()` 内部无条件 `requestLayout()`（即使宽高是 match_parent 由父决定），会向上冒泡让 RecyclerView 在滑动中的某一帧做一次**整屏 measure/layout**。回看时图片命中内存缓存、在 bind 期间同步 setImage，布局与 bind 同一趟完成所以无感。
- **修法**：新增 `ui/widget/PosterImageView`，在 setImageDrawable/setImageBitmap/setImageResource 调用期间置 `suppressLayoutRequest=true`，覆写 `requestLayout()` 在该期间只 `invalidate()` 不冒泡；`sizeFixedByParent()`（宽高都不是 WRAP_CONTENT 才拦）保留自适应场景。item_grid / item_search_card 的 ivThumb 改用它。
- 同版附带：Picasso `.noFade()`（默认 200ms 淡入，一屏十几张同时 alpha 混合）、GridFragment 加大 RecycledViewPool（`setMaxRecycledViews(0, min(max(8,span*2),14))`，默认仅 5）。
- **不要做**：静态共享 RecycledViewPool（ViewHolder 持有旧 Activity View → 泄漏）；`fit()`；`pauseTag/resumeTag`；`setInitialPrefetchItemCount`。这四条都在 2.28.1/2.28.2 试过且回退。
- 构建验证 BUILD SUCCESS（双架构签名通过），提交 87b973a，**未推送**。
- 若仍掉帧的下一步候选：① 把 item_grid 的 ShadowLayout 两层 clipPath 换成 `clipToOutline` + ViewOutlineProvider（去掉每帧 new Path）；② 海报 `.config(Bitmap.Config.RGB_565)` 砍半纹理带宽（有轻微色带）。

### v2.28.4 真正的 CPU 抢占源：Picasso 用共享重任务线程池（2026-11-03 夜）
- **用户反馈**：2.28.3 后「新内容刷出来那一下仍掉帧，但比之前好很多」。
- **关键发现（推翻了我原本打算做的 RGB_565）**：`OkGoHelper.initPicasso` 早就配了 `.defaultBitmapConfig(Bitmap.Config.RGB_565)`，所以改变位图格式没有收益，**改前必须查现状，别重复优化**。
- **真凶**：`.executor(HeavyTaskUtil.getBigTaskExecutorService())` —— 解码用的是应用重任务池 `CORE_POOL_SIZE = max(2, min(CPU-1,3)) + 2`（4 核=5，最大 6）。4 核平板上等于占满所有核心，滑动时解码与 UI/RenderThread 抢 CPU。完美匹配现象：回看（无解码）流畅、新图出现（需解码）掉帧。
- **修法**：`imageDecodeExecutor()` 独立池，固定 4 线程 + `Process.setThreadPriority(THREAD_PRIORITY_DEFAULT + 1)`（nice+1 让位渲染）+ `allowCoreThreadTimeOut(true)` 空闲 30s 回收 + 命名线程 `picasso-decode`。
- **注意**：Android 的 `Process.setThreadPriority` 是 nice 值，**越小越优先**，所以「降优先级」要 +1，别写成 -1（那是提权）。
- Picasso 的 executor 线程同时承担网络下载（`MyOkhttpDownLoader.load` 是同步阻塞），所以线程数不能砍太狠（3 会让图出现变慢，取 4）。
- 构建验证 BUILD SUCCESS（双架构签名），提交 d6b5a5d，**未推送**。
- 仍掉帧的下一步（按预期收益排序）：① 滑动时把 OkHttp 图片下载并发限到 ≤6（现在 `maxRequestsPerHost(32)`，15 张图同时 TLS 下载很吃 CPU）；② item_grid 去掉两层 ShadowLayout 的 `clipPath`（每帧 new Path）改 `clipToOutline`；③ 扁平化 item_grid 层级（去掉中间 RelativeLayout + 年 badge 的 ShadowLayout）。

### v2.28.5 「切分栏后滑不动 + 内容掉一截」真因（2026-11-03 夜）
- **现象**：用户横滑切到另一个分栏后，上滑列表不动，只说「从上往下掉一部分内容」；起初以为机型差异，实测两台平板都有 → 是代码问题。
- **真因（不是触摸冲突！）**：`Utils.getPosterSpanCount` 大屏能排 6~7 列，一屏约 20 张卡片，而源一页通常正好 20 条 → **列表没有可滚动余量**。`BaseQuickAdapter.setOnLoadMoreListener` 依赖「滚到最后一个」才回调，于是**永远触发不了下一页**，列表卡死在第一页；上滑没有余量时只在 Android 12+ 触发**过卷拉伸（stretch overscroll）**，视觉上就是「内容被拽下去一截」。
- **修法**：`GridFragment.autoFillViewport()`——数据落盘后 `postDelayed(90ms)` 检查 `canScrollVertically(±1)`，不能滚且 `page <= maxPage` 就自动补下一页，最多连续 3 页；`mAutoFilling` 标志用于抑制自动补页时的「没有更多了」Toast；`onFragmentResume` 也补一次检查（旋屏改列数后可能又不满屏）。
- 顺带修：后台刷新回来不再无脑 `setNewData`（会让 RV 重新布局、把浏览位置拽走）→ `sameVideoIds()` 相同则跳过；真变化时 `replaceDataKeepingScroll()` 记录 `findFirstVisibleItemPosition + getTop() - paddingTop` 再 `scrollToPositionWithOffset` 还原。
- **排查教训**：不要一上来就怀疑 ViewPager 触摸拦截/嵌套滚动——先用「列表到底能不能滚」验证。`canScrollVertically` 为 false 的老列表 + 上拉加载 = 死锁组合，大屏/多列布局特别容易踩。
