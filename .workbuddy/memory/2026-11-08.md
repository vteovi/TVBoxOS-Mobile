## v2.32.1 首页「启动后闪一下、卡片位置突然变」

用户现象：打开软件后往上滑一下，过几秒首页会闪一下，卡片位置像突然变了。

三段成因（都指向"启动时的静默刷新打断浏览"）：

1. **GridFragment 第一页静默刷新整表替换**
   - `initData` 先铺 `grid_cache_<sourceKey>_<sortId>` 的缓存（立即能滑），随后 `requestList()` 拿网络第一页。
   - `handleListResult` 里 `shownFromCache=true` 时走 `replaceDataKeepingScroll()`：`gridAdapter.setNewData()` → `notifyDataSetChanged`，所有可见卡片重新 bind（海报若 URL 变了会先回占位图 → 闪）。
   - 「最近更新」类分类的新片插在最前面，新旧 id 序列不同 → 整片换位置。
   - 更糟的是 `replaceDataKeepingScroll` 的恢复条件写成 `firstPos > 0`：只滑一点点时第一行还露着（`findFirstVisibleItemPosition()==0`），条件不成立 → 偏移不恢复，列表视觉上"往上跳一下"。

2. **HomeFragment 分类数据回来时整页重建**
   - `sortResult` observer 用 `oldSortIds.zip(newSortIds).all { 相等 }` 判断结构，**顺序变化**也算不同 → `initViewPager(absXml)` 会 `fragments.clear()` + 换 adapter，所有分栏 Fragment 重建、列表回顶并闪一下。
   - 重新 `install(...)` 还可能让 TabLayout 的当前项复位。

3. **`initData()` 无条件 `showLoading()`**
   - LoadSir 会把整块 `contentLayout`（含 ViewPager 和所有 RecyclerView）从布局树上摘下来换成 loading 页，再 `showSuccess()` 放回去 —— 已有内容时调用就是一次可见闪烁 + 重新布局。

修法：
- `GridFragment`：新增 `userBrowsing()`（`canScrollVertically(-1)` 或 `findFirstVisibleItemPosition()>0`），用户已离开顶部时**不替换列表**，只写缓存（`Hawk.put(cacheKey())` 在判断之前，已经落盘），下次进入该分栏再生效。
- `replaceDataKeepingScroll`：`firstPos > 0` → `firstPos >= 0`；offset 改用 `getDecoratedTop(first) - paddingTop`（`getTop()` 不含 item margin/decoration）。
- `HomeFragment`：结构判断改成「id 集合」比较（`toSet()`），集合相同就不重建；顺序也相同时才把 `mSortDataList` 换成新对象（拿最新的 filters/name），顺序不同时保留旧列表保持 tab 与 fragment 对应。
- `initData()`：`if (fragments.isEmpty()) showLoading()`，已渲染过分栏不再切 loading 页。

版本 2.32.0/362 → **2.32.1/363**（PATCH）。`更新记录.md` 已写 `### 2.32.1 — 2026-11-08`，CI 可抽 4 条 changelog。
校验：本机无 JDK/SDK，仅静态检查（Java 括号剥字符串后平衡、Kotlin 大/圆括号计数配平、`userBrowsing`/`keepFragments` 等符号引用、版本号与 changelog 抽取）。**未真实编译**。

## v2.32.2 分栏切回保持滚动位置（并入 2.32.1 未发布版本）

用户：首页第一个分栏滑到第二个，再滑回第一个，会闪一下并跳到最顶部；要求"原来在什么位置回来还是什么位置"。

原因：`GridFragment` 完全没有保存滚动位置。切走时 `onFragmentPause()` 是空实现；滑回来 `onFragmentResume()` 里只补 observer / 补 autoFill / 重建 LayoutManager。ViewPager 重新 attach fragment view 时 RecyclerView 会丢锚点（或 `applyGridLayoutManager()` 重设 LayoutManager），直接从第一条重新布局 —— 表现为闪一下 + 回顶。

改法（`GridFragment`）：
- 新增 `mSavedFirstPos` / `mSavedOffset`，`saveScrollState()` 记录 `findFirstVisibleItemPosition` + `getDecoratedTop(first) - paddingTop`；在 `onFragmentPause()` 和 `onDestroyView()`（被 FSPA 销毁前）各存一次。
- `restoreScrollState()`：`cur == saved && offset 相同` 时直接 return（不打扰用户刚滑的新位置），否则 `scrollToPositionWithOffset`；目标位置按 `getItemCount()-1` clamp，防数据变少时越界。
- `onFragmentResume()` 末尾先同步调一次（下一轮 layout 直接落到正确位置，避免先画一帧顶部），再 `post` 一次兜底。
- `initData()` 是主动回顶部（换分类/筛选/切源），清空记忆，否则下次 resume 会被旧位置拽回去。
- `autoFillViewport()` 增加 `getChildCount()==0` 守卫：切回瞬间列表还没布局，`canScrollVertically` 恒为 false 会被误判「一屏没填满」多发一次分页请求。

版本：2.32.1/363（未发布）→ **2.32.2/364**，更新记录把 2.32.1 段落直接改成 2.32.2，避免留下一个从未发布的版本段落。
校验：本机无 JDK/SDK，仅静态检查（括号、符号引用、版本号、changelog 6 条 586 字）。未真实编译。

## v2.32.3 首页刷新改为差量更新（取代 2.32.2 的「不刷新只写缓存」）

用户反馈两点：① 不喜欢刷新时「闪一下 + 卡片突然变位置」，更怕按下的瞬间卡片换成了另一部；② 之前为避开闪烁做的「用户已上滑就不刷新、只在切分类/换源时才生效」不能接受，要求刷新照常、但只更新卡片。

参考项目：`D:/Project/TVBoxOS_Portrait`（同一套 TVBoxOS 代码的早期分支，版本 1.14.0/104）。
对比结论：**它没有更好的做法** —— `GridFragment` 的 `listResult` 观察者同样是 `gridAdapter.setNewData(...)` 整表替换，adapter 还更朴素（每次都 `cancelRequest` + 重新 `load`），结构上也一样是 `FragmentStatePagerAdapter`。所以那边"看着没问题"只是因为新片插入少、缓存命中后图片不重新解码，不存在专门的位置保持逻辑。可复用的只有它 `applySpanCount()` 里「只在列数变化时才重建 LayoutManager」这个思路。

根因（闪 + 跳位是同一件事的两个表现）：
- `setNewData` = `notifyDataSetChanged`，所有可见卡片重新 bind；本 adapter 有 `TAG_PIC_URL` 守卫，图片地址没变不会重请求，但**新插入的条目**是新影片 → 必定重新加载海报 → 视觉上闪。
- RecyclerView 只按**位置索引**保留锚点（`LinearLayoutManager.updateAnchorFromChildren`），新片插在最前面时同一索引换了内容 → 整片换位；手指按住的那张卡也换了影片。

改法（`GridFragment`）：
- 新增 `updateFirstPage()` / `applyFirstPage()`：`DiffUtil.calculateDiff(..., true)` 后 `getData().clear()+addAll()` 再 `dispatchUpdatesTo(gridAdapter)`，只派发真正的插入/移动/内容变化；`areContentsTheSame` 只比 `year/name/note/pic(trim)`，避免无意义 rebind。
- 套用前记录**锚点影片 id** + `getDecoratedTop(first) - paddingTop`；套用后按 id 找新索引再 `scrollToPositionWithOffset` → 正在看的卡片原地不动。在顶部（`!canScrollVertically(-1)`）不做锚定，直接 `scrollToPositionWithOffset(0,0)` 让新条目出现在最前面。
- 列表 `getScrollState() != SCROLL_STATE_IDLE` 时先存 `mPendingFirstPage`，`OnScrollListener` 收到 IDLE 再套用；分栏切走期间收到的刷新在 `onFragmentResume` 的 post 里「先还原位置再套用」（切走时套用会因为不可见布局信息不准而顶回顶部）。
- 点击/长按改为 `mGridView.getChildAdapterPosition(view)` 取数据（回调里的 position 可能是绑定时的旧值），并做 `NO_POSITION` 与越界保护。
- 全部定位运算从 `instanceof GridLayoutManager` 换成 `LinearLayoutManager`：`V7GridLayoutManager` 的继承链无法离线确认，用父类判断更稳，且用到的都是 Linear 级方法。
- 删除 `sameVideoIds()` / `userBrowsing()` / `replaceDataKeepingScroll()`。

版本：2.32.2/364 → **2.32.3/365**（PATCH）。`更新记录.md` 新增 `### 2.32.3`（4 条 363 字），并把 2.32.2 首条改成只描述成因、指向 2.32.3 的改法。
校验：本机无 JDK/SDK，仅静态检查（Java 括号剥字符串后平衡、符号引用、版本号、changelog 抽取）。**未真实编译**。

## v2.32.4 平板首页「闪一下 + 内容整体往下挪」

用户：平板上 2.32.3 之后仍然会「闪一下，然后突然变动位置，好像往下拉了一下」，而 `D:/Project/TVBoxOS_Portrait` 不会。

**为什么 Portrait 不会**：它根本没有「打开后刷新第一页」这条链路（`shownFromCache` 时直接 `setNewData`，且只在 `initData()` 里触发），也没有 `autoFillViewport`。不是它做对了，是它不做这件事。

**四个叠加成因（本次全部修掉）**：

1. **顶部不锚定（主因）** — 2.32.3 的 `applyFirstPage` 里 `boolean atTop = !canScrollVertically(-1)`，「在顶部就不锚定、直接 `scrollToPositionWithOffset(0,0)`」，想让新片直接出现在最前面。但「最近更新」这类分类一次插进 4~8 条新片，首屏所有卡片整体下移 N 行。手机一屏 10 来张只挪一两行不明显；平板一屏 20+ 张，整屏位移 → 用户感知成「被往下拉了一下」。**平板上一页 20 条 ≈ 一屏，`canScrollVertically(-1)` 常为 false（内容不足一屏滑不动），所以永远走这个分支**。
   改法：去掉 `atTop` 特判，**始终**按第一张可见卡片的影片 id + `getTop()-paddingTop` 锚定。
2. **截断已加载的后续页** — `target.clear(); target.addAll(data)`，而 `data` 只有第一页。用户滑动中刷新被 `mPendingFirstPage` 暂存期间，`loadMore`/autoFill 已经追加了第 2、3 页，停下来套用时把这几十条一起删了 → 列表突然变短、位置被拽走。改法：`data` + `old` 尾部按 id 去重合并后再 diff。
3. **主线程写缓存** — `Hawk.put(cacheKey(), GsonUtils.toJson(list))`：Gson 序列化 20 条 + Hawk 内部 `SharedPreferences.commit()` 同步落盘，大屏数据多时白掉一帧 = 「闪一下」。改法：`cacheFirstPageAsync()` 里主线程只做 `new ArrayList<>(list)` 快照，序列化和落盘丢给 `HeavyTaskUtil.executeNewTask()`。
4. **海报 URL 随机参数** — `trimPic` 只 trim，源给 pic 拼时间戳/随机参数时 `areContentsTheSame` 全 false → 整批重绑重载图 → 闪。改法：比较前截掉 `?` 之后的部分。

**顺带**：锚点 id 找不到（源下架）时按 `anchorOldPos * newSize / oldSize` 比例估算位置，不再跳回顶部；`mPendingFirstPage` 的 post 里再判一次 `getScrollState()==IDLE`，这一帧用户又滑起来就重新暂存。

**排查时排除掉的**：`fragment_grid.xml` 无 ItemDecoration（间距是 item 的 `layout_margin="3dp"`，`getTop()` 与 `getDecoratedTop()` 等价）；`overScrollMode="never"`，不是过卷回弹；`tv_selectedItemIsCentered="true"` 两边工程都有、不是差异；`applyGridLayoutManager` 用 `screenWidthDp` 算列数，不依赖测量，`mConfigChanged` 只在配置变化时置位。

## v2.32.5 首页「闪 + 往下拉一下」：不再补偿位置，改成不碰列表

用户：2.32.4 之后「还是有，没看到变化」。说明前四版都在 GridFragment 的数据补偿路径上打转，实际情况要么补偿永远有残差，要么根因不在那条链路上。

**这次的判断**：只要「刷新后把位置补回去」，就永远有误差；平板一屏 20+ 张卡、首行贴屏幕顶边，误差会被放大成整屏位移。所以改成**后台刷新完全不改正在显示的列表**（`shownFromCache` 时第一页只 `cacheFirstPageAsync`，不碰 adapter），从物理上消除「闪 + 位移」的可能。用户原话也支持这个语义：「切分类 / 换源才刷新首页」。

**同时补掉的三条旁路**（都不在 GridFragment 里，解释了为什么之前改 GridFragment「没看到变化」）：

1. `BaseLazyFragment.showSuccess()/showLoading()/showEmpty()` 原来无状态下判断，LoadSir 每次 `showCallback` 都会把目标视图从根布局摘掉再挂回；而 `GridFragment.initView()` 是 `setLoadSir2(mGridView)`——**LoadSir 直接注册在 RecyclerView 上**，所以每次状态回调 = 列表 detach/attach 一次 = 闪一下。现在用 `mLoadState` 记录，重复设置直接 return（`setLoadSir/setLoadSir2` 里初始化为 Success，因为 register 后内容视图就在显示）。
2. `HomeFragment.sortResult` 重建 ViewPager 时（分类集合变化）会把所有分栏重建、跳回第一栏；现在先用**旧的** `oldSortIds` + `tabLayout.currentItemIndex` 记下 id（注意 `mSortDataList` 那时已被换成新列表，不能拿它查），`install()` 后按 id 停回原栏；`HOME_REC==2`（关闭主页）时索引前后各偏移 1。
3. 主页推荐：`sortResult` 回来会 `f.setHomeSourceRec()` + `refreshHomeRec()`（= `setNewData` 整表替换，而主页就是第一栏，用户很可能正在看）；豆瓣热门更是网络回调几秒后才到、也 `setNewData`。两处都改成「只更新字段/缓存，列表为空时才 setNewData」。

**删除**：`updateFirstPage` / `applyFirstPage` / `VideoDiffCallback` / `mPendingFirstPage` / `mPendingApplyScrollListener` / `bindPendingApplyListener` / `DiffUtil` import（-241 行）。保留 `cacheFirstPageAsync`、滚动位置记忆还原。

**排查时确认排除的**：`PosterCardLayout.onMeasure` 按 `widthSize` 强制 2:3（或 16:9）定高，item 高度是确定的，图片晚到不会改变行高；`item_grid` 无 ItemDecoration。

版本 2.32.4/366 → **2.32.5/367**（PATCH），`更新记录.md` 新增 `### 2.32.5`（4 条）。校验：本机无 JDK/SDK，只做静态检查（三个 Java 文件剥字符串+注释后括号平衡 0/0、符号引用、版本号、changelog 抽取、`更新记录.md` 行尾统一回 CRLF）。**未真实编译**，需用户本机构建。

## 重建本地编译环境（JDK 17 + Android SDK 34）

前置：机器上 `java`/`adb`/`sdkmanager`/`winget`/`choco`/`scoop` 全都没有，`C://Java`、`C://Android` 也不存在（与 11-07 记忆里"编译链不可见"一致）。有 curl/unzip，C 盘剩 60G。

装法（全部免安装 zip，不写注册表）：

1. **JDK**：清华 Adoptium 镜像 `https://mirrors.tuna.tsinghua.edu.cn/Adoptium/17/jdk/x64/windows/OpenJDK17U-jdk_x64_windows_hotspot_17.0.21_9.zip`（183M，9 秒下完，比 github release 快很多）→ 解压后把 `jdk-17.0.21+9` 重命名为 `C://Java//jdk-17`。
2. **cmdline-tools**：`https://dl.google.com/android/repository/commandlinetools-win-11076708_latest.zip`（147M）→ 解压到 `C://Android//Sdk//cmdline-tools//latest`（zip 内层目录就叫 `cmdline-tools`，必须改名 `latest`，否则 sdkmanager 认不到）。
3. `yes | sdkmanager --licenses`；再装 `platform-tools`、`platforms;android-34`、`build-tools;34.0.0`（compileSdk 34 / AGP 8.5.2 默认 build-tools）。
4. 用户级环境变量：`JAVA_HOME=C://Java//jdk-17`、`ANDROID_HOME`/`ANDROID_SDK_ROOT=C://Android//Sdk`，PATH 追加 `jdk-17\bin`、`platform-tools`、`cmdline-tools\latest\bin`。
5. `local.properties` 原本就写着 `sdk.dir=C:////Android//Sdk`，根目录 `build_apk.ps1` 里也硬编码了这两个路径 → 都不用改，双击脚本即可构建。

- `./gradlew assembleArm64v8Debug` → BUILD SUCCESSFUL in 17m45s（首次含依赖下载，`~/.gradle` 1.2G），产物 44M，`apksigner verify` 通过（CN=TVBoxOSC）。
